# Технический аудит Unofficial Channel Atlas

Дата аудита: 3 ноября 2026 года. Объект: исходный архив `tg-parser.rar`, исходные конфиги и статический экспорт 779 каналов.

## Итог

Проект уже имел полезную основу: раздельные модули сбора, HTML-парсинг, PostgreSQL, транзакцию на канал, ограниченный retry/backoff и статический интерфейс. Основные проблемы были не в отсутствии архитектуры, а в нескольких несогласованных контрактах между БД, экспортом, классификатором и картой.

После изменений в проекте:

- исправлен экспорт типа канала и добавлена трассировка решений классификатора;
- подсказка из каталога отделена от канонического региона;
- региональный классификатор стал консервативнее и объяснимее;
- географическая карта использует проекцию Ламберта и фиксированный масштаб;
- федеральные и неизвестные каналы больше не растягивают географическую плоскость искусственными полосами;
- восстановлен синтаксически повреждённый файл тематических ключевых слов;
- тяжёлые ML-зависимости вынесены из базовой установки;
- обновлена документация, добавлены тесты и отчёт для ручной проверки.

## Найденные проблемы и исправления

### 1. `channel_type` терялся при экспорте — исправлено

`exporter._channel_to_row()` пытался прочитать `channel_type`, но `db.get_channels_with_meta()` не выбирал это поле. В результате все каналы в `web/data/channels.json` экспортировались с `channel_type = null`, хотя в другом JSON-кэше типы уже присутствовали. Фронтенд использует это поле для цветов, счётчиков и легенды.

**Изменение:** запрос БД теперь выбирает `channel_type` и поля аудита классификации; экспорт сохраняет значения и приводит отсутствующий тип к `unknown`.

### 2. Географическая карта была негеографической — исправлено

Старая реализация:

- использовала `x = longitude`, `y = -latitude` без компенсации искажений;
- случайно размещала точки внутри радиуса до трёх градусов, что для России означает очень большие смещения;
- ставила федеральные и неизвестные каналы в горизонтальные полосы;
- сохраняла всё в `semantic_map.json`, смешивая два разных типа раскладки;
- фронтенд приводил карту к квадрату `1600 × 1600`, игнорируя фактическое соотношение сторон.

**Изменение:** геокарта теперь выводится в отдельные `geo_map.json/js`, использует коническую проекцию Ламберта, фиксированный охват всех субъектов, компактное детерминированное смещение точек и реальные размеры полотна. На карту попадают только региональные каналы с известными координатами. Прочие каналы остаются в общем каталоге.

**Что пока не сделано:** реальные контуры страны и субъектов. Текущий слой — точки по географическим центрам, а не полноценная картографическая подложка. Для административных границ потребуется отдельный лицензированный GeoJSON/TopoJSON.

### 3. Регион и подсказка каталога были смешаны — исправлено

В `config/channels.json` поле `region` часто содержало город (например, `Казань` или `Екатеринбург`). При этом в БД то же поле использовалось как результат классификации — субъект РФ. Повторный `scrape` мог подменить уже нормализованный регион значением из каталога.

**Изменение:** добавлено отдельное поле `region_hint` в конфиг, модель и БД. `pipeline.upsert_channel()` обновляет только подсказку и больше не перезаписывает канонический `region`. Старое имя `region` в конфиге пока поддерживается как fallback для обратной совместимости.

### 4. Старый региональный матчинг давал ложные назначения — переработано

Старая версия выбирала совпадение по приоритету поля и длине ключа, плохо обрабатывала составные названия, а упоминание пяти регионов в описании превращало канал в `federal`. В отдельном файле хранилась ещё одна версия словаря регионов, не используемая классификатором.

**Изменение:** создан единый `region_classifier.py` на основе `region_aliases.py`. Он:

- анализирует название, username, описание и подсказку отдельно;
- поддерживает многословные названия и контекст описания;
- не расширяет короткие неоднозначные слова до префиксов (`луга`/`луганск`, `чита`/`читает`);
- распознаёт коды в username с разделителями (`okidoki_spb`);
- при конфликте близких регионов оставляет канал без региона;
- считает федеральными только username из `federal_channels.json`;
- сохраняет список кандидатов, оценку, источник и объяснение.

Для однозначных сложных исключений добавлен `config/region_overrides.json`. Ручные правила имеют приоритет над эвристикой.

### 5. `topic_keywords.py` был оборван — исправлено

Исходный файл завершался посреди строкового литерала и не проходил `compileall`. Поиск по проекту не обнаружил его использования в текущем пайплайне. Файл восстановлен как автономный эвристический тематический классификатор, но намеренно не подключён к основному сбору без отдельной проверки качества рубрик.

### 6. Категория кандидата игнорировалась — исправлено частично

`discover.py` записывал каждый найденный канал как `subcategory=general`, даже если внешний каталог помечал его как экономику или политику.

**Изменение:** добавлено сопоставление известных внешних рубрик с внутренними (`Экономика` → `business`, `Политика` → `politics` и т.д.). Неизвестные рубрики остаются `general`, чтобы не присваивать тему без основания.

### 7. Базовая установка включала тяжёлые ML-пакеты — исправлено

`sentence-transformers`, `umap-learn` и `scikit-learn` были обязательны, хотя основная геокарта их не использует.

**Изменение:** базовые зависимости оставлены в `requirements.txt`; MTProto, семантическая раскладка и API вынесены в отдельные optional requirements-файлы.

### 8. Документация не соответствовала коду — исправлено

В README присутствовали отсутствующая CLI-команда, описание остановки пагинации по `new_count == 0` (такого условия в коде не было), дубли и некорректный служебный markup. Документация переписана по текущей реализации. Добавлен минимальный `api.py`, соответствующий режиму API в `web/api.js`.

## Повторная классификация исходного набора

На 779 каналах из приложенного статического экспорта, с подсказками из каталога и whitelist из `config/federal_channels.json`, получилась следующая картина:

| Результат | Количество |
|---|---:|
| Региональные | 597 |
| Федеральные (явный whitelist) | 15 |
| Неизвестные / требующие проверки | 167 |
| **Всего** | **779** |

Все 597 классифицированных региональных записей имеют координаты в `region_geo.py`, поэтому попали в подготовленный `geo_map`. Неизвестные не исключены из каталога: они доступны в поиске и списке.

Из 167 неизвестных каналов у 36 есть альтернативные региональные кандидаты, у 131 недостаточно географических признаков. Рабочая таблица для модерации: `reports/region_review.csv`. Это предложение алгоритма, не ручная верификация: список федеральных каналов, неоднозначные случаи и автоматические назначения требуют проверки владельцем каталога.

## Технические проверки исходного рефакторинга (историческая проверка v0.5.x)

- `python -m unittest discover -s tests -v` — 11 тестов пройдены;
- `python -m compileall -q main.py api.py src tests` — пройдено;
- `node --check` для `web/app.js`, `web/layout.js`, `web/map.js`, `web/api.js` — пройдено.

**Не выполнялось:** подключение к пользовательскому PostgreSQL, миграция реальной БД, сетевой запуск парсера против Telegram и визуальная проверка в полноценном браузере. В среде аудита не было конфигурации пользовательской БД и установленного `psycopg2`; поэтому результат интеграции следует проверить на копии БД до применения на рабочей базе.

## Рекомендуемый план развития

### Этап 1 — завершить качество каталога

1. Просмотреть `reports/region_review.csv` и заполнить `config/region_overrides.json` для спорных каналов.
2. Проверить `federal_channels.json`: критерий должен быть единым — общероссийская/межрегиональная редакция или явно заданная вручную категория, а не просто крупный канал.
3. Добавить регрессионный тест для каждой исправленной ошибки региона.
4. Вынести классификацию в отдельный административный сценарий проверки новых и изменившихся каналов.

### Этап 2 — сделать настоящую карту

1. Подключить векторный слой границ субъектов РФ с лицензией и происхождением данных.
2. Рисовать контуры регионов и точки каналов в одной проекции.
3. Добавить масштабирование по региону, подписи регионов и выбор региона по клику.
4. Для крупных скоплений (Москва, Санкт-Петербург) перейти от случайного jitter к кластерным маркерам с раскрытием списка при zoom-in.

### Этап 3 — расширить типы каналов

Сейчас каталог почти полностью состоит из новостных каналов. До масштабирования стоит определить устойчивую таксономию, например: `category` — класс источника/сообщества, `subcategory` — тематика. Сохранять исходную категорию внешнего каталога и источник происхождения записи, не смешивать эти значения с вычисленными рубриками. Нужны статусы активности, дата обнаружения, дата последней проверки и правила слияния дублей username.

### Этап 4 — аналитика постов и сводки

Сбор постов уже существует и сохраняет базовые поля в `posts`, но нет слоя аналитики публикаций. Рекомендуемое развитие:

1. Нормализовать публикацию: язык, текст, время, исходная ссылка, тип медиа, идентификатор сообщения и дата изменения.
2. Дедуплицировать публикации между каналами (сначала URL/точные хеши, затем BM25/эмбеддинги с порогом и ручной проверкой пар).
3. Классифицировать тематику, географию и тип события отдельно от классификации самого канала.
4. Группировать похожие посты в события, объединять пересказы одного события из нескольких источников.
5. Генерировать сводки с цитируемыми ссылками на исходные посты и оценкой качества/полноты.
6. Ввести редакторскую модерацию перед автоматической публикацией сводок.

### Этап 5 — надёжность и эксплуатация

- вынести загрузку в очередь задач и ограничивать скорость по домену/каналу;
- хранить историю изменений метаданных, чтобы видеть рост/падение подписчиков и переименование;
- добавить структурированные логи, отчёты ошибок и метрики успешности парсинга;
- добавить резервное копирование PostgreSQL и миграции по версиям;
- зафиксировать зависимости lock-файлом и добавить CI с unit-тестами.

## Вывод

Проект уже содержит базу для дальнейшей аналитики постов, поэтому переписывать его с нуля нецелесообразно. Приоритет — довести качество каталога и географическую привязку, затем добавить настоящий географический слой и только после этого строить дедупликацию событий и генерацию сводок. Такой порядок уменьшит риск, что ошибки в исходном каталоге будут автоматически размножаться в аналитике.

# Дополнение: реализация версии 0.7.0

## Что добавлено

- Единый реестр `channel_candidates` с независимыми связями `channel_candidate_sources`; повторное обнаружение из разных источников не создаёт дубль по нормализованному username.
- Поиск TGDen вынесен в отдельный adapter с набором запросов в `config/discovery_queries.json`, лимитом до 100 результатов на запрос и задержкой 1,5 с. Публичный endpoint описан сторонней документацией адаптера, но не был протестирован прямым сетевым запросом из среды сборки.
- Импорт CloudSeeding реализован через пользовательский CSV/TSV/JSON-экспорт, без обхода авторизации или paywall.
- MTProto-коннектор использует отдельную локальную сессию резервного аккаунта в `sessions/`; команды read-only. Добавлены импорт подписок, рекомендации Telegram и ограниченный сбор постов. После первой авторизации необходимо закрепить Telegram ID в `TG_EXPECTED_USER_ID`; до этого чтение блокируется.
- `mtproto-scrape` пишет в существующую таблицу `posts`; дубликаты устраняются тем же уникальным ключом, что и в HTML-пайплайне. За запуск — не более 25 каналов и 100 сообщений на канал.
- Добавлена нормализация числовых значений с суффиксами `K`, `тыс.`, `млн`, `млрд`.
- Временные ограничения HTTP 429/403 при проверке кандидатов не маркируют их как окончательно удалённые.
- TGDen поддерживает как experimental catalog endpoint, так и legacy suggest fallback; для последнего тестируется формат групп `channels`.
- Добавлено закрепление ожидаемого user ID резервного Telegram-аккаунта; MTProto-чтение без `TG_EXPECTED_USER_ID` заблокировано.
- В таблицу `channel_sources` при импорте копируются исходные source URL и метаданные.
- Повторное обнаружение уже импортированного кандидата обновляет рабочую запись канала и добавляет новый provenance source без дубля.
- CLI справка (`python main.py --help`) доступна до установки PostgreSQL-драйвера за счёт отложенных импортов.

## Технические проверки версии 0.7.0

- `python -m unittest discover -s tests -v` — 30 тестов пройдены.
- `python -m compileall -q main.py api.py src tests` — пройдено.
- `node --check` для `web/app.js`, `web/layout.js`, `web/map.js`, `web/api.js` — пройдено.

## Ограничения проверки

- PostgreSQL не был доступен; миграция схемы и SQL на реальном сервере не выполнялись.
- Нет резервного Telegram API ID/HASH и авторизованной Telethon-сессии; авторизация, реальные рекомендации, сбор публикаций и поведение FloodWait в сети пользователя требуют отдельного smoke-test.
- TGDen endpoint не был запрошен напрямую из среды упаковки; adapter сначала пробует экспериментальный `GET /api/catalog`, а при 404/405 использует старый публичный `GET /api/suggest`. Первый короткий запрос должен подтвердить фактический ответ. Для `/api/catalog` доступна сторонняя, но не официальная документация.
- CloudSeeding протестирован на синтетических русских/английских CSV/JSON структурах; реальный экспорт пользователя не предоставлен.

## Использование данных и условия Telegram

Перед запуском массовых операций MTProto необходимо проверить применимость текущих Telegram Terms. В частности, Content Licensing Terms запрещают scraping/indexing/aggregation данных с платформы для AI/ML-разработки и deployment, за узким исключением индивидуального явного и продолжающегося согласия пользователей в определённом контексте. Семантическая карта использует embeddings и снижение размерности, поэтому не должна строиться на Telegram-origin данных без применимых прав и согласий.


## Дополнение: проверка tgden API от 03.11.2026

Контрольные запросы `новости Казани`, `Казань` и `crypto` к `GET /api/catalog` вернули один и тот же набор из 10 записей. Идентификаторы имеют формат `demo-000000`…`demo-000009`, а `telegram_id` равен нулю. Это свидетельствует о демонстрационном/запасном наборе, а не о рабочем поиске по переданному запросу. В версии 0.7.1 такой payload распознаётся и не записывается. После этого выполняется ограниченная проверка `/api/suggest`; её реальная пригодность требует проверки в пользовательской среде, поскольку этот endpoint также не имеет подтверждённого публичного контракта.

Отдельно: диагностический PowerShell here-string, переданный оператором `| python`, преобразовал кириллицу в `?` до формирования URL (`q=%3F...`). Поэтому результаты русских запросов именно этого диагностического запуска нельзя использовать для оценки русскоязычного поиска. При этом корректный ASCII-запрос `crypto` вернул тот же demo-набор, что и подтверждает проблему `/api/catalog`. Для дальнейших русскоязычных тестов код диагностики следует сохранять в UTF-8 файл и запускать как `python .\script.py`, а не передавать через конвейер stdin.
