# Первый этап: воспроизводимость и PostgreSQL

Реализован по согласованному первому пункту [плана](ROADMAP.md). Проверка: 11 ноября 2026 года. Рабочая база владельца и локальные выгрузки не изменялись.

## Результат

- Чистая установка и обновление прежней базы проходят через версионированные миграции, с SHA-256 и общей транзакцией. Существующие записи не заменяются конфигурацией.
- Параллельные миграции сериализуются, повторный запуск ничего не меняет. При ошибке откатываются и DDL, и история. Более новая/изменённая история не принимается молча.
- Есть команда `db-status` и отдельный `/api/ready`. Готовность проверяет реальное подключение, историю и рабочие таблицы/колонки, без автоматического изменения схемы.
- Для базового режима, API и разработки закреплены версии и хеши зависимостей. Есть универсальные маркеры Python/ОС и GitHub Actions для Python/PostgreSQL и браузера.
- [DATABASE.md](DATABASE.md) содержит порядок обновления, перенос на сервер, пробное восстановление и возврат к резервной копии.

## Подтверждённые проверки

| Проверка | Результат |
|---|---|
| Модульные тесты в чистых закреплённых окружениях Python 3.10 и 3.12 | 92 проверки пройдены в каждом; 22 интеграционных теста пропускаются без DSN и запускаются отдельно |
| Реальный PostgreSQL 16.15 / Python 3.12 | 22 интеграционных теста, без пропусков |
| Реальный PostgreSQL 17.11 / Python 3.10 и 3.12 | 22 интеграционных теста в каждом окружении, без пропусков |
| Базовый lock без FastAPI | 91 модульная проверка пройдена; API-проверка и PostgreSQL-набор корректно пропущены |
| `pip check` в чистых dev-окружениях | Конфликтов нет |
| Ruff E9/F и compileall | Успешно |
| Canvas и Chromium | Раскладка 2200 точек, hit-testing и браузерные сценарии пройдены |
| CLI `init-db → init-db → db-status` | Версия 0002, ожидающих миграций нет |
| Обязательный runner без DSN | Ошибка с кодом 2, а не ложный успешный запуск |
| Полный `pg_dump -Fc → pg_restore` на PostgreSQL 16 | Все записи 7 таблиц совпали; история/курсор сохранились; выдача нового ID работает |

Фактическую версию PostgreSQL определяли у запущенного сервера. Образы разных версий запускались последовательно из-за ограничения диска среды. Текущие состояния автоматических прогонов доступны в [GitHub Actions](https://github.com/zEeZja/tgatlas/actions/workflows/checks.yml).

В интеграционном наборе проверяются реальная SQL-ошибка и откат имени/метаданных/постов/курсора, пакетная дедупликация более 500 записей, смена username при том же Telegram ID, конфликт идентичностей, внешние ключи, продолжение сбора после переподключения и API с настоящими данными. Только ответы Telegram/профиль в этих сценариях подменены: сетевой сбор не является частью проверки БД.

Для обновления использованы подлинный SQL-снимок коммита `621a14e` с тестовыми записями и прежний актуальный `db/schema.sql` без истории миграций. После обновления сверены строки всех старых таблиц, ID и курсоры. Изменённые SQL-файлы, испорченная история, неудачная миграция и одновременный запуск двух initializers проверены отдельно.

## Границы

Личная рабочая база не восстанавливалась и не мигрировалась в этой среде. Перед обновлением на сервере нужно проверить **её отдельную копию**, как описано в инструкции. Восстановление резервной копии проверено на контролируемых тестовых данных, а не на архиве владельца.

Windows учтена маркерами зависимостей и проверкой контрольных сумм при CRLF, но нативный Windows-прогон не выполнялся. Необязательные Telethon/ML-пакеты не входят в закреплённые снимки базового режима и API.

Готовность API не проверяет Telegram, свежесть данных, права записи и все индексы. Автоматических обратных миграций нет: для полного возврата используется резервная копия и соответствующий код.

Этапы 2–5 (качество классификации, очередь обновления, масштабирование карты, сводки) в этот набор изменений не включены.
