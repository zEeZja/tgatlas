# PostgreSQL: установка, обновление и восстановление

Этот документ описывает первый этап плана стабильности. [Результаты проверки реализации](STABILITY_STAGE_1.md). Рабочая БД остаётся источником истины; статическая выгрузка не является резервной копией.

## Что изменилось

- `python main.py init-db` применяет `db/migrations/0001_legacy_baseline.sql`, затем `0002_scrape_checkpoints.sql`. Первая миграция совместима с прежними таблицами и дополняет отсутствующие элементы. Вторая фиксирует таблицу курсоров, которая раньше могла создаваться при чтении.
- `schema_migrations` хранит версию, имя, SHA-256 и время применения. Все ожидающие миграции и их история применяются одной транзакцией. Ошибка откатывает весь пакет; рабочие таблицы не удаляются и не очищаются.
- Два параллельных `init-db` сериализуются транзакционной advisory-блокировкой. Ожидание блокировок ограничено 10 секундами: при превышении команда завершается ошибкой и откатом, её можно повторить после устранения причины.
- Изменённые применённые SQL-файлы, пропуск версии в истории или база новее кода вызывают ошибку. Не правьте контрольные суммы для обхода проверки.
- Приложение и API не запускают миграции автоматически. Это отдельный шаг развёртывания.

`db/schema.sql` оставлен как совместимый снимок. Для установки используйте `init-db`, чтобы создавалась и проверялась история. Схема снимка и результат миграций сравниваются интеграционным тестом. Старые ручные запросы `db/cleanup_*.sql` не являются миграциями и автоматически не выполняются.

## Чистая установка

Создайте пустую базу, настройте `PG_*` в `.env`, установите закреплённые зависимости и выполните:

```bash
python -m pip install --require-hashes -r requirements/locked-base.txt
python main.py init-db
python main.py db-status
```

`db-status` ничего не меняет. Код `0` — история актуальна, `1` — есть ожидающие миграции либо ошибка. При наличии полной схемы без истории команда всё равно предложит `init-db`, чтобы безопасно принять существующую базу под управление миграциями.

## Обновление существующей базы

1. Остановите задания записи: scrape, refresh-metadata, импорт и планировщик. На время DDL также желательно остановить API, чтобы его запросы не удерживали блокировки.
2. Сделайте резервную копию и проверьте, что она читается:

```bash
pg_dump -h localhost -U postgres -d tg_parser -Fc -f atlas-before-upgrade.dump
pg_restore --list atlas-before-upgrade.dump
```

`--list` проверяет читаемость архива, но не заменяет пробное восстановление. Параметры подключения должны соответствовать вашей базе; утилиты берутся из PostgreSQL bin. На Windows можно указать полный путь через PowerShell `& "C:\Program Files\PostgreSQL\16\bin\pg_dump.exe" ...`.

3. Вначале восстановите копию в **отдельную тестовую базу**, настройте подключение к ней в отдельной копии проекта и проверьте обновление:

```bash
pg_restore -h localhost -U postgres -d tg_parser_upgrade_test --no-owner --no-privileges --exit-on-error atlas-before-upgrade.dump
python main.py db-status
python main.py init-db
python main.py init-db
python main.py db-status
python main.py stats
```

Второй `init-db` должен сообщить, что схема актуальна. Сравните записи/статистику с исходной копией. Не указывайте тестовое имя базы только в pg_restore, оставив приложение подключённым к рабочей: переменная `PG_DATABASE` приложения тоже должна указывать на тестовую базу.

4. После успешной проверки копии обновите код и зависимости рабочего экземпляра и выполните `init-db`, затем `db-status`, `stats` и `export`. Запустите API и задания. Для обновления с версии до миграций записи остаются на своих местах, а история создаётся при первом запуске.

В рамках этого этапа обновление проверено на синтетических записях и настоящей схеме предыдущего коммита `621a14e`, а также на прежнем актуальном снимке без истории. Личная база владельца не переносилась и не изменялась; локальная копия перед обновлением нужна для выявления её особенностей.

## Восстановление после неудачного обновления

Если `init-db` завершился SQL-ошибкой, пакет миграций откатывается автоматически. Устраните причину и повторите команду. Если нужна полная отмена уже успешно применённого обновления, надёжный путь — восстановление резервной копии и соответствующей версии кода. Автоматического `down` нет: обратные DDL-преобразования могут терять данные.

Не восстанавливайте архив поверх заполненной рабочей базы. Создайте отдельную пустую базу:

```bash
createdb -h localhost -U postgres tg_parser_recovered
pg_restore -h localhost -U postgres -d tg_parser_recovered --no-owner --no-privileges --exit-on-error atlas-before-upgrade.dump
```

Переключите `PG_DATABASE` на восстановленную базу, используйте версию кода на момент резервной копии, проверьте `stats`, затем возвращайте сервис в работу. Новые записи, сделанные после копирования, не входят в этот архив; поэтому при обновлении задания записи останавливают. Базу с неудачным обновлением сохраните отдельно до завершения проверки.

## Перенос на сервер

Переносите репозиторий, нужные значения `.env` и дамп `pg_dump -Fc`. Восстановление включает таблицы, индексы, последовательности, историю миграций, кандидатов, источники, публикации и курсоры. PostgreSQL на принимающей стороне должен быть совместим с источником; предпочтительно та же основная версия либо более новая. Утилита pg_dump должна поддерживать версию сервера источника.

```bash
pg_restore -h 127.0.0.1 -U atlas -d tg_parser --no-owner --no-privileges --exit-on-error atlas-backup.dump
python main.py db-status
python main.py init-db
python main.py stats
python main.py export
```

Получатель должен быть пустым; `init-db` перед `pg_restore` не требуется. Пароли и архивы не коммитятся в Git и не размещаются в `web/`. Дамп сохраняет и таблицу миграций, поэтому на сервер нужен соответствующий код. База новее выбранного кода не будет автоматически понижена.

## Готовность API

| Маршрут | Значение |
|---|---|
| `/api/health` | Процесс отвечает; база не проверяется |
| `/api/ready` → 200 | БД доступна, история актуальна, рабочие колонки/таблицы доступны |
| `/api/ready` → 503 | Подключение, схема или история не готовы |

Ответ ошибки не содержит DSN, пароля или SQL-текста. Подключение ограничено `PG_CONNECT_TIMEOUT` (по умолчанию 5 секунд), отдельные SQL-запросы готовности — 3 секундами. Готовность не проверяет доступность Telegram, актуальность метаданных и все индексы: это отдельные задачи. Для успешной проверки нужен доступ пользователя приложения к таблицам и истории; это не тест его прав на запись.

## Реальные интеграционные тесты

Нужна **отдельная временная БД**. Для подключения тесты используют только `ATLAS_TEST_DSN`, без подстановки настроек подключения из `.env` или `PG_*`. Каждый тест создаёт уникальную схему `atlas_test_<uuid>`, работает только в ней и удаляет её после проверки. У пользователя должны быть права CREATE в тестовой базе. При аварийном завершении может остаться схема с таким именем.

Пример PostgreSQL 16 в Docker (учётные данные только тестовые):

```bash
docker run -d --name atlas-test-db -e POSTGRES_PASSWORD=atlas_test_only -e POSTGRES_DB=atlas_ci -p 127.0.0.1:55432:5432 postgres:16-bookworm
docker exec atlas-test-db pg_isready -U postgres -d atlas_ci
```

После готовности сервера, Linux/macOS:

```bash
export ATLAS_TEST_DSN='host=127.0.0.1 port=55432 dbname=atlas_ci user=postgres password=atlas_test_only'
python -m pip install --require-hashes -r requirements/locked-dev.txt
python scripts/run_postgres_tests.py
```

PowerShell:

```powershell
$env:ATLAS_TEST_DSN = 'host=127.0.0.1 port=55432 dbname=atlas_ci user=postgres password=atlas_test_only'
python -m pip install --require-hashes -r requirements/locked-dev.txt
python scripts/run_postgres_tests.py
```

После завершения тестовый контейнер можно удалить вместе с его тестовым томом: `docker rm -fv atlas-test-db`. Это не команда для рабочего контейнера.

Обязательный runner завершается ошибкой при отсутствии DSN, недоступности PostgreSQL, пустом наборе тестов или пропусках. Обычный `unittest discover` без DSN пропускает интеграционный набор; это удобно для разработки, но не считается проверкой PostgreSQL.

GitHub Actions запускает закреплённые зависимости, модульные тесты, обязательный набор на PostgreSQL 16/Python 3.10 и PostgreSQL 17/Python 3.12, цикл CLI и отдельную проверку Canvas/браузера.

## Добавление миграции

Создайте новый SQL-файл с увеличенной четырёхзначной версией, например `0003_add_metadata_index.sql`. Применённые файлы не переименовывают и не исправляют; исправление оформляют новой миграцией. Обновите совместимый снимок `db/schema.sql`, тесты и документацию.

Миграции выполняются в одной транзакции: `CREATE INDEX CONCURRENTLY`, явные `COMMIT` и другие операции вне транзакции для этого runner не подходят. Крупные преобразования требуют отдельного плана и проверки времени блокировок. Перед выпуском проверьте чистую установку, повторное применение, обновление копии предыдущей схемы и откат при ошибке.
